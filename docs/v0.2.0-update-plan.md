# dsh-secure-audit 对比分析与 v0.2.0 更新方案

> 日期：2026-08-22 ｜ 基线版本：v0.1.1（已发布）
> 对比对象：`toby-bridges/api-relay-audit`（v2.4，798★，AGPL-3.0，Python）
> `PerryLink/dsh-auto-review`（main，78★，Apache-2.0，TypeScript）
> 用途：为 dsh-secure-audit 下一次版本更新提供依据；本文档本身不修改代码。

---

## 〇、一句话结论

dsh-secure-audit 的三个能力（注入检测 / PII 脱敏 / 本地审计）在**纯规则 + 只读**定位上
已经做得很扎实（零依赖、防误报结构校验、脱敏证据、可复现报告），但对比两个对标项目，
缺的是**四件事**：

1. **主动验证维度**（api-relay-audit 有 14 步运行时探测，我们是纯静态检查）
2. **fail-closed 与风险分级**（dsh-auto-review 默认拒绝 + riskLevel，我们 fail-open 且无风险级）
3. **决策可重建的审计链**（dsh-auto-review 每次裁决可从会话日志重建；我们只有单向日志）
4. **结构化上下文脱敏**（dsh-auto-review 递归键名脱敏工具参数；我们只做固定类型的正则脱敏）

## 二、对标 A（api-relay-audit）的亮点与可借鉴点

### A1. 主动探测 ≠ 静态检查（最大差距）

api-relay-audit 会真实地向 relay 发送 14 组探测请求，检测：
- prompt injection / prompt extraction / instruction override / jailbreak 抵抗
- **context truncation（上下文截断）**、**tool-call substitution（工具调用替换）**
- **error leakage（错误泄露）**、**SSE stream anomalies（流异常）**
- **model substitution signals（模型替换信号）**：self-ID、延迟方差、上游通道指纹

我们目前是纯静态：`security_scan_text` 只扫给定文本，`security_audit` 只读本地文件。
**启发**：本地只读约束下，可以补一个「**DSH 本机运行时自检**」维度——例如对本地
`dsh web` 服务做只读连通性/版本/能力探测（不写盘、不发真实业务流量），或者把
「上下文截断」「错误泄露」这类**信号**做成规则引擎的新 category。

### A2. 证据边界（evidence boundary）理念

A 明确区分「**信号**」（self-ID、延迟、通道指纹——只是 consistency signal）与
「**证明**」（raw response JSON、request IDs、stream signatures、透明日志哈希）。
报告里 `inconclusive` 不会被当作 `clean`。

**启发**：我们的 `security_scan_text` 返回 `decision/confidence`，但没有给 agent
「这是规则信号还是模型确认」的分层。v0.2.0 可以在结果里增加 `evidenceTier`
（`rule-only` | `classifier-confirmed`），并保持「规则命中 ≠ 安全结论」的措辞纪律。

### A3. 透明日志（transparent forensic log）

A 的审计运行会写 append-only JSONL：每条请求只记 **SHA-256 哈希**（不存 body），
URL、状态码、响应头、传输元数据，条目 ≤1.5KB，避免凭据静态风险。

**启发**：我们已有结构化 JSONL logger（requestId 关联），但没记「输入哈希」。
可以在 `security_scan_text` 输出里带上 `inputSha256`（缓存键本来就在算），
让任何一次裁决都可以在本地重放验证——「决策可重建」的第一步。

### A4. 错误串脱敏（redact_error）

A 的日志层把所有错误串剥掉响应体内容（只留错误类型 + HTTP 状态），
防止 curl 输出里夹带的 API key / 上游 URL 进日志。

**启发**：我们的 `runClassifier` 错误只拼了 `err?.name`（已收敛），
但 `audit.js` 的 `checkNetworkBindings` 会把 env 值 slice 40 字符进证据——
虽然经过 `sanitize()`（PII 脱敏 + 路径归一），但建议对「URL 型证据」再补一层
`redactError` 风格的剥壳，和 A 对齐。

### A5. 双通道分发（standalone + 模块化）+ 22 个 CLI flags + 808 测试

A 用 build 脚本生成零依赖 standalone `audit.py`（curl 传输），模块化版本另有
808 个 pytest。我们「源码即产物」已经够简洁，但**测试规模**（74 vs 808）差距明显——
不必追数量，但要补**端到端/回归快照测试**（例如用 fixture 会话目录跑 `security_audit`，
断言报告结构不回归）。

### A6. profile 化（general / web3 / full）

A 用运行时 profile 隔离不同探测深度；Web3 检查默认关闭（profile-gated）。

**启发**：我们可以给 `security_audit` 加 `profile` 参数（`quick` | `full`），
quick 只跑低成本检查，full 才做完整文件遍历——大仓库下用户体验更好。

## 三、对标 B（dsh-auto-review）的亮点与可借鉴点

### B1. fail-closed 默认（与我们相反）

B 的审查子代理崩溃/超时/schema 不符 → `fallbackPolicy: rejected`（默认拒绝），
只有显式配置才降级为 delegate / allow-once。我们恰恰相反：`security_scan_text`
超时 → 降级 `allow`（fail-open）。

**启发**：产品语义不同（它是审批闸门，我们是检测工具），但**应该给用户选择权**：
v0.2.0 给 scan 增加 `onTimeout: 'allow' | 'review' | 'block'` 配置（默认保持 allow
兼容现状），敏感流程可以设成 fail-closed。这直接补掉 README 里「fail-open 不可配置」的短板。

### B2. 风险分级 riskLevel（我们有 confidence，但没有风险级）

B 的裁决带 `riskLevel: low|medium|high`，配合 `riskPolicy`（`maxAutoAllow: high`、
`onHighRisk: delegate`）做策略路由。

**启发**：我们的规则表已有 severity（info/low/medium/high/critical），完全可以从
「命中规则的最大 severity + 累计置信度」推导一个 `riskLevel` 字段输出。这样
`security_scan_text` 的消费者（包括未来的自动放行策略）就有了分级依据。

### B3. 递归键名脱敏（sanitizeArguments）——最值得抄的一手

B 在把工具参数送给审查子代理前，**递归遍历 JSON**：任何键匹配
`api_key|token|secret|password|authorization|credential|private_key...` 就整值替换为
`[REDACTED]`。这是「结构感知」脱敏，我们目前只有「类型感知」正则脱敏。

**启发**：给 `security_redact_text` 增加 `mode: 'json'`（或新工具
`security_redact_json`）：对 JSON 输入做**递归键名脱敏 + 值类型脱敏**双通道，
再保留 PII 正则兜底。这直接服务 DSH 场景——agent 要把工具参数/会话上下文交给
第三方模型前，先过一遍结构化脱敏。这是 v0.2.0 最实打实的新能力。

### B4. 决策可重建（session-log reconstruction）

B 的每个裁决都能从会话日志重建：`approval/asked → autoReview/verdict → approval/decided`，
事件带 `ignorable: true` 信封标记；还有 invariant 伴生组件校验「标记 ⟺ 事件」一致性。

**启发**：我们的日志是单向 JSONL（只有 scan/redact/audit 事件）。v0.2.0 可以：
1. 每条 scan 事件记录 `inputSha256 + rulesetVersion + 生效阈值` —— 决策可重放；
2. 审计报告输出 `reportSha256`（自校验防篡改/防误传）；
3. 可选加一个 `invariant` 导出（dsh-tools 已提供 `./invariant` 入口）——
   校验「日志里的 decision 与 rulesetVersion 一致的输入重扫结果相同」。

### B5. schema 加载时校验

B 在模块加载时 `assertObjectJsonSchema(VERDICT_SCHEMA)`，schema 回归会**在加载时炸掉**
而不是运行时才发现。dsh-tools 0.1.0-rc.7 已导出 `assertObjectJsonSchema`。

**启发**：v0.2.0 对我们 index.js 里的三个 output schema 做同样的加载时校验，
CI 里也能提前抓 schema 漂移。

### B6. 断路器 + 预算（circuit breaker / budgets）

B 有 3 连拒或 10 中 6 拒触发 delegate 的断路器，以及 per-turn 的
`maxReviewsPerTurn` / `maxFailuresPerTurn` 预算。

**启发**：我们的 `security_audit` 有 `sampleLimit`（预算的雏形）。可以扩展为
`fileBudget`（扫描文件数上限）+ `byteBudget`（累计字节上限），避免超大仓库拖死
工具执行（当前 60s timeout 是兜底，但更精细的预算能提前优雅降级）。

### B7. 版本能力探测

B 会探测 host 是否支持 `ignorable` 信封标记（peer 版本线预检 + 首次 append 探测），
不支持则降级，避免会话不可恢复。

**启发**：我们的 peer 是 `dsh-tools >= 0.1.0-rc.7`，但对 host 能力（如
`skills` 服务是否存在、`dsh-session` 是否支持某标记）没有探测。
v0.2.0 可以在 apply() 时收集一份「host capability probe」结果，进 `security_audit`
报告（新增一个 `host-capabilities` 检查），让用户一眼看到当前 host 缺什么。

## 四、dsh-secure-audit 现状不足清单（按影响排序）

| # | 不足 | 影响 | 对标来源 |
| --- | --- | --- | --- |
| 1 | fail-open 不可配置，超时必降级 allow | 敏感流程无法 fail-closed | B1 |
| 2 | 无 riskLevel，只有 confidence | 下游策略无法分级处置 | B2 |
| 3 | 无结构化/键名感知脱敏 | JSON 工具参数/会话上下文无法整体脱敏 | B3 |

| 6 | 审计检查无 profile/预算分级 | 大仓库检查慢、结果不分轻重 | A6 |
| 7 | 无 host 能力探测 | 用户不知道当前 host 缺什么能力 | B7 |

| 12 | 审计报告无可复现自校验哈希 | 报告可被误传/篡改而不自知 | A3 |

## 五、v0.2.0 优化方案（按 P0/P1/P2 分级）

### P0 — 低风险高收益，随 v0.2.0 发布（✅ 2026-08-22 已全部实施，93/93 测试通过）

1. **scan 增加 `riskLevel` 输出**（B2）
   - 规则：取命中规则最高 severity 映射 + 置信度修正；`critical→high`、`high→high`、
     `medium→medium`、其余 `low`（置信度 < reviewThreshold 且无命中 → `low`）。
   - 改动：`lib/injection.js` 计算并返回；`index.js` schema 增加字段；README/CHANGELOG。

2. **scan 增加 `onTimeout` 配置**（B1）
   - 新配置 `onTimeout: 'allow' | 'review' | 'block'`，默认 `'allow'`（向后兼容），
     `'block'` 时预算超时直接 block + 警告，供敏感流程 fail-closed。
   - 改动：`lib/injection.js` DEFAULT_OPTIONS + scan() 分支；README 配置表。

3. **新增 `security_redact_json`（结构化脱敏）**（B3，本次最大新能力）
   - 输入：`{ json: <string|object>, keyModes: string[]?, maskChar? }`
   - 逻辑：解析 JSON → 递归遍历，键名匹配敏感词（复用 audit.js 的 SECRET_KEY_RE 族）
     整值替换为 `[REDACTED]`；值内再跑 PII 正则兜底；保留结构（key 不脱敏）。
   - 输出：`{ redactedJson: string, replacedKeys: [{path, key}], piiCount }`。
   - 改动：`lib/redact.js` 新增 `redactJson`；`index.js` 注册第 4 个工具；
     测试全覆盖（嵌套对象/数组/转义/非法 JSON）。

4. **scan 结果带 `inputSha256`**（A3/B4 起步）
   - 复用缓存键；输出字段 `inputSha256`；README 说明「可本地重放验证」。

5. **schema 加载时校验**（B5）
   - index.js 对三个 output schema 调 `assertObjectJsonSchema`（dsh-tools 已导出）；
     回归即在启动时炸。

6. **audit 报告带 `reportSha256`**（A3）
   - 报告 JSON 序列化后算哈希放进报告顶层；README 说明自校验用法。

### P1 — 中等成本，v0.2.x 系列（按需分批）

7. **`security_audit` 增加 `profile: 'quick' | 'full'`**（A6）
   - quick：只跑 config/env/network 低成本检查 + 文件采样减半；
   - full：默认全量（当前行为）。

8. **新增 `host-capabilities` 检查**（B7）
   - apply() 探测并缓存：dsh-tools 版本、skills 服务可用性、session 能力标记；
     审计报告新增一项检查，展示「当前 host 支持什么/缺什么」。

9. **错误串证据剥壳**（A4）
   - `checkNetworkBindings` 的 env 值证据改用「键名 + 是否绑定」而非 slice 值；
     或对 URL 型证据先过 `redactError` 风格剥离。

10. **端到端回归快照测试**（A5）
    - 新增 `tests/fixtures/fake-dsh/`（mini 配置/会话/插件目录）+ 快照断言
      （同一目录两次 `security_audit` 报告字节级一致、结构不回归）。

11. **README.zh.md + 中文示例**（A/B 多语言）
    - 中文 README、中文 usage 示例、中文分类器配置说明。

### P2 — 长期 Roadmap（合并现有 Roadmap）

12. **注入规则表扩充**：新增 `context-truncation`、`error-leakage`、
    `tool-rewrite` 信号类别（A1）——规则形态的静态近似，覆盖 A 的部分探测意图。
13. **决策可重建增强**：scan 事件落 `inputSha256 + ruleset + thresholds`，
    invariant 导出（dsh-tools `./invariant`）校验重放一致（B4）。
14. **Prometheus 指标**（既有 Roadmap）：拦截率/误报率/P99。
15. **规则灰度发布**（既有 Roadmap）。
16. **NER 辅助脱敏**（既有 Roadmap）：姓名/地址。
17. **DSH llm 分类器适配器**（既有 Roadmap）：默认适配器接入 DSH `llm` 服务。

## 六、版本与发布建议

- **v0.2.0（minor）**：P0 全做。新增 1 工具（`security_redact_json`）+ scan 两处增强
  （`riskLevel`、`onTimeout`）+ 报告哈希/输入哈希 + schema 加载校验。
  破坏性：无（新字段/新配置/新工具，全部向后兼容）→ 但按「0.x minor 留给新能力」惯例走 minor。
- 发布前清单沿用 v0.1.1 流程：`npm run lint` + `npm test` 全绿 → `npm pack --dry-run`
  → 推送 main + tag → Release 工作流 → npm publish。
- dsh.so 收录条目版本无关（url/name/category/description），**无需重新提交 PR**。

## 七、待用户确认的取舍

1. `security_redact_json` 是**新增第 4 个工具**，还是**并入 `security_redact_text`
   的 `mode` 参数**？（建议新工具，schema 更清晰，向后兼容）
2. `onTimeout` 默认值保持 `allow`（现状）还是改 `review`（更保守）？
   （建议保持 `allow`，语义变化留到 v0.3 做破坏性升级）
3. P0 之外，`host-capabilities`（P1-8）是否值得提前到 v0.2.0？
   （建议做——成本低，对用户排查安装问题价值高）
